# ADR-002: 端末内データベースにSQLiteを採用する

- **状態**：承認
- **決定日**：2026-11-03
- **対象**：Windows Tauri デスクトップアプリ

## 背景

現行アプリは利用者情報と共通設定をIndexedDBに保存している。今後、担当者アカウント、監査記録、USBバックアップを追加するにあたり、端末内で一元管理する永続化方式が必要となる。

## 選択肢の比較

| 選択肢 | メリット | デメリット・留意点 |
|---|---|---|
| IndexedDBを継続 | 現行実装を活用でき、Web画面から扱いやすい。追加のDB導入が不要。Tauri版ではアプリのWebView領域に永続化できる。 | WebViewのアプリデータ領域に依存し、アプリデータの削除・初期化等で失われる可能性がある。追加データの整合性、移行、バックアップ運用を設計する必要がある。 |
| SQLiteを採用 | デスクトップアプリ内で扱えるファイル型DBで、トランザクションや構造化クエリを利用できる。データとバックアップの管理を明示しやすい。 | DB連携・スキーマ管理・移行処理の実装と保守が必要。DBファイルの保護、暗号化、バックアップ整合性は別途設計が必要。 |

## 決定

追加開発後の端末内データベースとしてSQLiteを採用する。現行のIndexedDBからの移行方法と実施時期は別途設計する。SQLite連携ライブラリ、スキーマ、マイグレーション方式は実装前のデータ・アーキテクチャ設計で決定する。

## 理由

- Windowsデスクトップアプリのローカル保存先として、データを一元管理できる。
- 利用者情報、アカウント、設定、監査記録をトランザクションで整合的に扱いやすい。
- USBバックアップ・復元の対象を明確にしやすい。

通常のブラウザーキャッシュ消去でTauri版のIndexedDBが消えることを、SQLite採用の理由とはしない。保存データの消失には、いずれの方式でもバックアップが必要である。

## 影響・留意点

- IndexedDBに保存済みの利用者情報・共通設定をSQLiteへ移行する計画が必要。既存データを失わない移行・検証方法を定める。
- SQLite自体は暗号化を保証しない。保存データの暗号化、鍵管理、バックアップ暗号化は別のセキュリティ設計で決める。
- Rust側とフロントエンド間のデータアクセス境界、トランザクション責任、スキーマ変更手順を実装前に明確にする。
