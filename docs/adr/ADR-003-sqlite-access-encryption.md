# ADR-003: SQLiteへのアクセス境界と暗号化方式

- **状態**：承認
- **決定日**：2026-11-06
- **対象**：Windows Tauri デスクトップアプリ
- **関連**：ADR-001（Tauri採用）、ADR-002（SQLite採用）

## 背景

ADR-002でSQLiteの採用を決めたが、Rust側とフロントエンド（WebView）の間のデータアクセス境界と、保存データの暗号化は未決定である。

CareDocLibは個人情報（氏名、生年月日、住所、被保険者番号、要介護度）を扱う。現行のCSPは外部スクリプトとインラインスクリプトを禁止し、capabilitiesは `permissions: []`（画面からTauri APIを呼べない）である。

## 選択肢の比較（アクセス境界）

| 選択肢 | メリット | デメリット・留意点 |
|---|---|---|
| A. JSから直接SQLiteを使う（tauri-plugin-sql） | 実装量が少ない。 | 画面に任意のSQLを実行できる権限を渡す。画面が乗っ取られると全データの読み出し・削除が可能になる。入力チェックを通らない書き込みを防げない。 |
| B. Rustのコマンド経由（rusqlite） | 画面からは決められた操作しか呼べない。入力チェックとトランザクションをRust側で必ず通せる。将来SQLCipherへ切り替えやすい。 | Rust側の実装・保守と、コマンド・受け渡しの型の設計が必要。 |

## 決定

1. **DBへのアクセスはRustのコマンド経由とし、ライブラリはrusqliteを使う。**
   - 画面（JS）はSQLを持たない。tauri-plugin-sqlなど任意のSQLを実行できるプラグインは導入しない。
   - capabilitiesはアプリ独自のコマンドのみ許可する。CSPは現行の設定を維持する。
   - Rust側は Command → Service → Repository の3層とする。PDF生成（pdf-lib）は画面側に残す。
2. **アプリによる暗号化は現時点では行わない。** 端末の保護はBitLockerとWindowsのログインパスワードに任せ、利用ガイドで推奨する。
3. **バックアップはRust側でファイルに直接書き出す。** 復元前の自動バックアップは、書き込み完了を確認してから置き換えを始める。現行のJSON形式（`caredoc-backup` v1）の読み込みは、IndexedDBからの移行が完了するまで残す。

## 理由

- 個人情報を扱うため、画面に渡す権限を最小限にすることを、実装量の少なさより優先する。現行のCSP・capabilitiesの方針とも一致する。
- アプリ内暗号化（SQLCipher＋Windows DPAPIによる鍵保護）は、同じWindowsユーザーなら鍵を自動で取り出せるため、BitLockerとログインパスワードに対する上乗せ効果が小さい。
- 一方で、鍵の紛失によるデータ消失の危険と、Windowsでのビルドの複雑さ（OpenSSL等）が増える。小規模な事業所では、漏えいよりデータ消失の方が起きやすいと判断した。

## 影響・留意点

- Rust側でコマンド、Service、Repository、受け渡しの型を実装する必要がある。
- DBファイルは暗号化されないため、端末のBitLocker有効化とWindowsのパスワード設定を運用の前提とする。
- ブラウザ版（ローカル実行版）はSQLiteに対応しない。
