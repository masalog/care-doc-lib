# ADR-004: 認証・認可および操作者識別の基本方針

- **状態**：承認
- **決定日**：2026-11-27
- **対象**：Windows Tauri デスクトップアプリ
- **関連**：
  - [ADR-001（Tauri採用）](ADR-001-platform-tauri.md)
  - [ADR-002（IndexedDB継続採用）](ADR-002-indexeddb-storage.md)
  - [ADR-003（データ保護およびデータ交換方針）](ADR-003-data-protection.md)

## 背景

CareDocLib は介護認定申請書の作成を行う Windows デスクトップアプリであり、利用者の個人情報を取り扱う。
現行版では認証機能がなく、アプリを起動するとそのまま利用者情報の閲覧・編集や PDF 作成を行える状態にある。

小規模事業所や複数担当者による端末共有・交替利用を想定すると、以下を防ぐ仕組みが必要となる。

- 離席中や別担当者が誤って操作・編集してしまう事故（誤操作防止）
- 他人の状態のまま操作してしまうこと（うっかりのなりすまし防止）
- 利用者情報や共通設定を誰が登録・更新したか分からない状態（操作者の識別）

一方で、[ADR-002](ADR-002-indexeddb-storage.md) および [ADR-003](ADR-003-data-protection.md) で決定した通り、CareDocLib はサーバーを持たない JS + IndexedDB 中心の構成（Rust は Tauri Runtime のみ）と、OS 標準機能（Windows ログイン・BitLocker）による保護を前提としている。

そのため、現行構成を維持したまま現実的な運用負荷で導入できる認証・認可方針を決定する必要がある。

## 選択肢の比較

### 1. 実装基盤の選択

| 選択肢 | メリット | デメリット・留意点 |
|---|---|---|
| **A. 現行構成（JS + IndexedDB）で実装する** | ADR-002 の方針（Rust 最小・JS 集約）を維持できる。新規外部ライブラリや Tauri 権限追加が不要。 | DevTools や IndexedDB 直接参照による改ざんまではアプリ単独で防げない（OS 側保護が前提）。 |
| B. Rust（Tauri IPC）や SQLite へ認証・DB を移す | UI から切り離した強い境界や改ざん耐性を作りやすい。 | ADR-002 の前提を大きく覆し、Rust 実装・スキーマ移行・権限管理の保守負荷が増える。 |

### 2. ロール構成の選択

| 選択肢 | メリット | デメリット・留意点 |
|---|---|---|
| **A. 1ロール（認証済みユーザー共通権限）** | デスクトップアプリ運用で冗長になりにくい。管理者不在によるロックアウト等の運用負荷を抑えられる。 | バックアップ復元やアカウント管理を特定者のみに制限することはできない（確認ダイアログ・自動退避で誤操作を防ぐ）。 |
| B. 2〜3ロール（担当者 / 管理者 / 監査担当者） | 機能単位で細かく操作制限できる。 | 小規模事業所や 1人1台利用では切り替え・アカウント復旧の手間が過剰になりやすい。 |

### 3. 操作者識別の記録方式

| 選択肢 | メリット | デメリット・留意点 |
|---|---|---|
| **A. レコード上の作成者・更新者記録（`createdBy` / `updatedBy`）＋ログイン中表示** | 実装が軽量で IndexedDB 構成をシンプルに保てる。 | 削除操作や PDF 出力・バックアップ操作の履歴までは残らない。 |
| B. 簡易操作履歴ストアの追加 | 削除や PDF 出力・ログイン履歴まで追える。 | ログ保存領域の肥大化対策や表示画面の追加が必要になる。 |

## 決定

### 1. 現行の JS + IndexedDB 構成のまま認証・認可を実装する

- 認証処理、セッション管理、アカウント保存、認可チェックは JavaScript と IndexedDB（＋ブラウザ標準の Web Crypto API）で完結させる。
- Rust 側への業務ロジック追加、SQLite への移行、Tauri capabilities の権限拡張、CSP の緩和は行わない。
- 保存データの暗号化は引き続き行わず、端末・OS レベルの保護（Windows ログインパスワード、BitLocker）に委ねる（[ADR-003](ADR-003-data-protection.md) 継続）。

### 2. ロールは 1ロール（全アカウント共通権限）とする

- ロールは単一（担当者共通権限）とし、管理者専用ロールや監査担当者専用ロールは設けない。
- **認証（Authentication）**：アカウントIDと **4桁の数字 PIN** によるログイン・ログアウトを行い、現在の操作者を特定する。PIN は平文保存せず `PBKDF2-SHA256` 等でハッシュ化し、連続失敗時のロックアウト（5回連続失敗で1時間の一時制限）を組み合わせる。
- **認可（Authorization）**：未ログイン・ロック中・未登録アカウントからは画面表示およびデータ操作・PDF生成・バックアップを実行させない「状態ベースのアクセス制御」とする。
- バックアップ復元などの影響が大きい操作は、ロール制限ではなく確認ダイアログと復元前自動バックアップ（[08-backup.md](../impl/08-backup.md)）で安全性を担保する。
- アカウントの追加・PIN変更・削除はログイン中ユーザーが実行できる（無効化状態は設けず削除に一本化する）。最後の 1 件を削除して初回登録状態へ戻す場合は、誤削除・乗っ取り防止のため現在の PIN 再入力を必須とする。

### 3. 操作者識別はレコード単位の記録（案A）を採用する

- 利用者データ（`members`）および共通設定（`settings`）に作成者・最終更新者情報（`createdBy` / `updatedBy` 等）を記録し、ログイン中の担当者名を画面に表示する。
- 独立した操作履歴ストア（案B）は本段階では導入せず、将来必要になった場合の拡張項目とする。

### 4. 15分無操作で自動画面ロックを行う

- 最後の操作から 15 分間経過した場合、自動的に画面をロックする。
- ロック解除には現在のログインユーザーの PIN 再入力を求める（別ユーザーへ切り替える場合はログアウトして再ログインする）。

---

## 理由

- **デスクトップアプリの運用実態への適合**：単一利用者や小規模事業所で配布・利用するデスクトップアプリでは、複数ロールの維持や鍵・監査管理よりも、シンプルな運用性と迷わない操作性が重要である。
- **既存資産・設計方針との一貫性**：[ADR-002](ADR-002-indexeddb-storage.md) の「JS 中心・IndexedDB 採用・複雑な移行を避ける」方針および [ADR-003](ADR-003-data-protection.md) の「OS 保護優先」と矛盾なく導入できる。
- **誤操作・なりすまし防止への十分な効果**：15 分ロックと操作者ごとのログインにより、離席中の誤操作や別人の状態での作業を防止し、いつ誰が更新したかを識別できる。

---

## 影響・留意点

- **脅威モデルの境界**：本方針は「通常の利用手順における誤操作・うっかりのなりすまし防止と操作者識別」を目的とする。同一 Windows アカウント上で開発者ツールや IndexedDB ストレージを直接操作する攻撃者からの防御・改ざん防止は対象外であり、OS アカウント分離と BitLocker による保護を前提とする。
- **既存バックアップ形式との互換性**：`caredoc-backup` v1 形式（[08-backup.md](../impl/08-backup.md)）は `MEMBER_FIELDS` / `SETTINGS_FIELDS` 以外のキーを未知項目として拒否する仕様のため、書き出し時に認証・更新者メタデータの扱いを分離し、既存バックアップファイルの復元互換性を維持する。
- **関連ドキュメントとの整合**：[ユースケース](../use-cases.md)・[機能要件定義書](../functional-requirements.md)・[品質要件定義書](../quality-requirements.md)・[基本設計書](../basic-design.md)・[画面設計書](../screen-design.md) は、本 ADR および [ADR-002](ADR-002-indexeddb-storage.md) / [ADR-003](ADR-003-data-protection.md) の方針に合わせて改訂した。

## 結果

```text
アプリ起動
  ↓
アカウント0件なら初回アカウント登録 ／ 1件以上ならログイン
  ↓
認証成功（sessionStorage にセッション保持・1ロール共通権限）
  ↓
業務画面（申請書PDF作成 / 管理画面 / アカウント管理）
  ├─ 画面・データ操作の入口でセッション検証（認可ガード）
  ├─ 保存時に createdBy / updatedBy を記録（案A）
  └─ 15分無操作で自動画面ロック → PIN再入力で解除
```

詳細なスキーマ、画面仕様、検証ルール、テスト観点は [実装設計書 09：認証・認可・操作者識別](../impl/09-auth.md) に定める。
