# CareDocLib 基本設計書

| 項目 | 内容 |
|---|---|
| 状態 | 初版・要確認 |
| 対象 | Windows Tauri デスクトップアプリ |

本書は、要件を実現するための画面・構成・データの基本方針を示す。具体的な暗号方式、DBスキーマ、画面レイアウトなどの詳細は後続設計で決定する。

## 1. システム構成

- Windows上で動作するTauriデスクトップアプリとする。フロントエンドは既存のHTML/CSS/JavaScriptを利用し、ネイティブ処理は必要な範囲に限定する。
- 利用者情報、設定、アカウント、監査記録は端末内に保存する。外部サーバーとの通信や端末間同期は行わない。
- PDF生成は既存のpdf-libと申請書テンプレートを利用する。
- 論理構成は次のとおりとする。

```text
画面（ログイン、申請、管理、監査）
        ↓
アプリケーション処理（認証、申請、設定、監査、バックアップ）
        ↓
Repository（データ保存・読込の抽象化）
        ↓
端末内ストレージ
```

追加開発後の端末内データベースにはSQLiteを採用する。画面・アプリケーション処理からRepositoryを介してアクセスする。SQLite連携ライブラリ、スキーマ、マイグレーション方式および現行IndexedDBデータの移行手順は、実装前に設計・検証する。

## 2. 利用者とアクセス範囲

| 利用者 | 基本設計上のアクセス範囲 |
|---|---|
| 担当者 | 利用者情報・共通設定の操作、PDF作成 |
| 管理者 | 担当者と同じ申請業務、担当者アカウント管理、バックアップ・復元。監査記録は閲覧できない |
| 監査担当者 | 管理者とは別の人・アカウントで、操作記録の閲覧のみ |

組織の責任者が監査担当者を任命し、アプリ外の手順で監査専用アカウントを設定する。アプリ内の権限確認を画面表示だけに依存させず、データ操作の入口でも確認する。アプリ認証はWindowsアカウントやファイルアクセスを分離しない。

## 3. 画面構成

| 画面 | 主な機能 | 状態 |
|---|---|---|
| ログイン | 担当者の認証、ログアウト | 追加 |
| 申請書作成 | 利用者選択、申請情報入力、PDF作成・プレビュー・保存・印刷 | 現行画面を拡張 |
| 利用者管理 | 利用者情報の登録・検索・編集・削除 | 現行管理画面 |
| 共通設定 | 共通設定の登録・編集 | 現行管理画面を利用 |
| アカウント管理 | 担当者アカウントの作成・停止・再設定 | 追加・管理者のみ |
| 操作記録 | 監査担当者による監査記録の検索・閲覧 | 追加・監査担当者のみ |
| バックアップ・復元 | USBへのバックアップ作成、検証、復元 | 追加・管理者のみ |

画面ごとの構成、遷移、入力項目、エラー表示は画面設計書で定める。

## 4. 主要処理

### 4.1 ログインと利用者操作

1. アプリ起動時にログイン画面を表示する。
2. 認証成功後、利用者の役割に応じた画面を表示する。
3. 利用者情報・共通設定の作成、変更、削除、アカウント管理、バックアップ・復元を監査記録に残す。
4. 30分間操作がなければロックし、再認証後に利用を再開する。

### 4.2 PDF作成

1. 登録済み利用者を選択する。未登録なら先に登録する。
2. 情報を確認・修正し、申請日等を指定する。
3. 区分変更の場合のみ申請理由を入力する。
4. テンプレート、座標データ、共通設定と入力内容からPDFを生成する。
5. プレビューで確認し、必要なら修正して再生成する。確定後に保存・印刷する。

役所への提出はアプリの対象外とする。

### 4.3 バックアップと復元

- 管理者がバックアップを作成し、暗号化して組織管理のUSBへ保存する。
- 復旧キーはバックアップ媒体と別に管理する。
- 復元時は完全性を検証し、管理者が対象を確認してから復元する。検証失敗時は復元しない。
- バックアップの頻度、対象データ、保持期間終了後の削除・媒体管理手順は運用設計で確定する。保持目標は過去12か月分。

## 5. 論理データ

| データ | 主な内容 | 備考 |
|---|---|---|
| アカウント | アカウント識別子、認証情報、役割、状態 | パスワード平文を保存しない |
| 利用者 | 申請書作成に必要な利用者情報 | 全担当者で共有 |
| 共通設定 | 申請書に適用する共通設定 | 共有・担当者も編集可能 |
| 操作記録 | 担当者、日時、対象、操作、結果、変更項目名 | 個人情報の値を記録しない。管理者操作を含む。5年間保持し、改ざんを検知可能にする |
| バックアップ情報 | 作成日時、対象、完全性検証結果 | データ本体は暗号化してUSBに保存 |

項目定義、識別子、関連、削除方式はドメイン・データ設計で定め、暗号化単位はセキュリティ設計で決定する。重要な技術選択は必要に応じてADRへ記録する。

## 6. エラー・保護方針

- 認証失敗、保存失敗、PDF生成失敗、バックアップ検証・復元失敗は画面に明示する。失敗を成功として扱わない。
- 保存データとバックアップを暗号化する。暗号鍵・復旧キーの生成、保管、変更、復旧方式はセキュリティ設計で決定する。
- 操作記録には個人情報の値を含めない。
- ログイン中は担当者が全利用者データを扱える。保存時暗号化は、ログイン中の利用者や稼働中端末からデータを隠すものではない。
- UIからデータベースへ直接アクセスせず、データ操作の入口で認証・権限を確認する。
- 利用者情報等の変更と対応する監査記録は同一トランザクションで保存し、片方だけ確定しない。
- バックアップ復元は検証後に切り替え、失敗時に現行データを不整合な状態にしない。

## 7. 未決事項・要確認

- 監査記録の検索・出力方法と、保存期間終了後の削除方法。
- 同一Windowsアカウント共有時のOS側保護、端末暗号化の運用要件。
- 管理者アカウントの復旧、パスワード再設定後のデータ・鍵復旧。
- SQLite連携ライブラリ、スキーマ、マイグレーション方式、既存IndexedDBデータの移行・検証手順。
- 暗号鍵管理、バックアップ対象と頻度。
- 対応Windowsバージョン、起動・PDF生成時間等の性能目標。
- 既存の初期データ投入を追加開発後も行うか、移行・初期化方法をどうするか。
